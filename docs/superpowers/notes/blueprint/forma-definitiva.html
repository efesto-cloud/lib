1La forma

Ogni progetto nasce così: un contract, un core e gli adapter. È uno spettro: le implementazioni delle porte possono stare nel core o in un adapter, e spostarle è spostare una cartella. La porta c'è sempre.

Le estensioni (un bus fra componenti nostri con canali sostituibili, un bootstrap condiviso fra più processi) e i job sono da definire: il materiale è in estensioni.md.

2Pacchetti e dipendenze

Cartelle 
apps/        composition root: webapp, processi Node, seed
packages/    contract, core, db (schema e migrazioni)
adapters/    <tecnologia>-adapter: d1, sqlserver, http, stub
  • app → adapter → core e contract; core → contract
  • Nessuno importa un'app; un adapter non importa un altro adapter
  • Nome degli adapter: @<scope>/<tecnologia>-adapter
  • Lo stub-adapter ha implementazioni sue e i dati finti (il seed locale); non lega i fake del core
Import e build
  • Niente barrel: ogni pacchetto esporta "./*" verso ./dist/*.js e si importa per percorso
  • Contract, core e adapter si compilano in dist/ (tsc --build + tsc-alias), con "sideEffects": false
  • Dentro un pacchetto si importa con l'alias ~/ e l'estensione .js; fra pacchetti per percorso, senza estensione
  • Le parti client importano il contract e core/rule/*; il resto del core lo importano solo la composition root e il codice .server.ts

3Il contract

Il contract è il bordo verso chi chiama: quello che chi chiama vede o manda. Dipende solo da zod e better-result, mai dal core. Le porte non ci stanno, perché parlano di entity: restano nel core. Ogni file contiene un simbolo, con export default; solo schema e tipo dell'input sono export con nome.

CartellaCosa contieneRegola
useCase.tsUseCase<I, R> ed ExecutionContext L'interfaccia degli use case vive qui, non in un pacchetto esterno. Due soli parametri, l'input e il Result; il contesto non è un generico ma il tipo ExecutionContext del progetto, uno per tutta l'app, con i campi opzionali dove una chiamata può non averli
useCase/<modulo>/I<Nome>.tsL'interfaccia dello use case e, nello stesso file, lo schema del suo input; se serve, <Nome>Output Schema e tipo hanno lo stesso nome, <Nome>Input. Uno use case può riusare l'input di un altro
useCase/<modulo>/Dati<X>.ts, useCase/Dati<X>.tsUna parte d'input comune Nel modulo se è del modulo, alla radice di useCase/ se è fra moduli; si compone con .extend. Anche i tipi generici come Pagina<T> stanno qui
useCase/<modulo>/<Modulo>UseCases.tsIl tipo del modulo: chiave → interfacciaUna riga per use case
registry.tsUseCaseRegistry, che compone i tipi dei moduli, e UseCaseResolver Una riga per modulo; niente declare module. La chiave è anche l'identificativo nel container
interface/I<Entità>.tsCiò che esce: un'entità serializzata, o una riga (ISyncLogEntry) Un'interface, senza suffisso Dto e senza schema: la produce il nostro codice
type/Union di stringhe, struct semplici, strutture particolari (un Record) Mai qualcosa che rappresenta un'entità: quello va in interface/
enum/<Tipo>.ts, dict/<Tipo>Desc.tsLa versione a runtime di una union, e le sue etichette { [K in Tipo]: K } e { [K in Tipo]: string }; negli schemi z.enum(<Tipo>Enum)
errors/Gli errori che compaiono nella Error di uno use case§5
<canale>/Gli schemi di un canale d'ingresso che non è uno use case (i payload di un processo esterno, la firma)Per chi li riceve sono un ingresso: restano schemi
// contract/src/useCase.ts
export type ExecutionContext = { member?: IMember };

export interface UseCase<I, R extends Result<unknown, unknown>> {
    execute(input: I, context: ExecutionContext): Promise<R>;
}

// contract/src/useCase/expenses/IApproveExpense.ts
export const ApproveExpenseInput = z.object({ expense_id: z.string() });
export type ApproveExpenseInput = z.infer<typeof ApproveExpenseInput>;

export default interface IApproveExpense
    extends UseCase<
        ApproveExpenseInput,
        Result<IExpense, ExpenseNotFoundError | InvalidTransitionError | ConflictError>
    > {}

4Use case

Fa
  • Riceve un oggetto del tipo dichiarato, mai argomenti posizionali, e il contesto: execute(input, ctx); ctx si omette quando non serve
  • Applica le regole di dominio attraverso le entity e le funzioni pure di core/rule/
  • Ritorna sempre un Result: Result<void, …> per un successo senza valore, Result<T, never> se non può fallire
  • Scrive dentro uow.runWithTransaction, e allora la sua Error comprende ConflictError
Non fa
  • Rivalidare la forma dell'input: tiene solo le regole del dominio, con i loro errori
  • Leggere richiesta, cookie, variabili d'ambiente
  • Modificare la v delle entity
TemaRegola
NomiInterfaccia I<Nome> nel contract, implementazione <Nome> in core/src/useCase/<modulo>/impl/, chiave "<modulo>.<Nome>". Nessun suffisso UseCase.
Implementazione@injectable() export default class <Nome> implements I<Nome>. Le dipendenze arrivano nel costruttore con @inject(InternalSymbols.Repo.<X>), InternalSymbols.Service.<X>, InternalSymbols.UnitOfWork. La firma di execute ripete il tipo del Result; l'input si destruttura.
Modulo<Modulo>Module.ts nel core: un oggetto chiave → classe, tipato UseCaseImplementations<<Modulo>UseCases>. L'install del core li stende tutti in un solo useCaseModule<UseCaseRegistry>: una chiave che manca, un'implementazione che non rispetta l'interfaccia o un modulo dimenticato non compilano.
Logica comuneUna funzione, non uno use case: in core/src/useCase/<nome>.ts se è fra moduli, in impl/<nome>.ts se è del modulo.
ComposizioneUno use case può usarne un altro: lo riceve per chiave, tipato sull'interfaccia (@inject("expenses.GetExpense") private readonly expense: IGetExpense), gli passa lo stesso ctx, e condivide la Unit of Work perché sono nella stessa risoluzione. Nessun ciclo.
Contestoexecute(input, context: ExecutionContext): il tipo è quello del contract. Porta interfacce, non entity: un'entity fuori dalla Unit of Work scriverebbe fuori dal patto. Chi agisce su sé stesso viene dal contesto, chi agisce su un altro ha l'id nell'input.

5Errori

export default class ExpenseNotFoundError extends TaggedError("ExpenseNotFoundError") {}
export default class ReceiptUploadError extends TaggedError("ReceiptUploadError")<{ cause?: unknown }> {}
DoveQuale errore
contract/src/errors/Compare nella Error di uno use case. Lo impone il compilatore, perché il contract non dipende dal core.
core/src/errors/L'errore di una porta che lo use case gestisce e non lascia uscire.
eccezioneI guasti dell'infrastruttura e gli errori di programmazione. Al bordo diventano un messaggio generico, con lo stack solo in sviluppo.
  • Forma nativa di better-result: TaggedError("<Nome>Error")<{ campi }>, con il tag uguale al nome della classe. Niente taggedError, niente schemi, niente codec. Un file per errore.
  • I campi solo quando servono a un messaggio più preciso; la causa si porta come cause?: unknown. Un <Entità>NotFoundError non ha campi.
  • Nomi in inglese: <Entità>NotFoundError, Invalid<X>Error, <X>TakenError, Incomplete<X>Error, Locked<X>Error, <X>Without<Y>Error, Outdated<X>Error.
  • Chi riceve distingue per _tag. I messaggi per l'utente stanno nell'app, in un Record<ErroreMostrato["_tag"], string>: un errore senza messaggio, o un messaggio senza errore, non compila. Un modulo nuovo i cui errori arrivano all'utente entra in ErroreMostrato.
  • Come un errore viaggia su un mezzo lo decide chi lo espone, quando serve: non il contract.

6Entity, repository e Unit of Work

È la prassi dell'architettura esagonale con Unit of Work e optimistic locking, scritta a mano perché nessun ORM copre bene insieme D1, Postgres, SQLite e MongoDB. Il patto è lo stesso su ogni database; lo snippet SQL è quello che funziona anche dove la transazione non è interattiva (D1).

PezzoIl patto
EntityLa base sta nel core del progetto: Entity<P, Id = string> con id, v, isNew() (v === 0), isRemoved() e il remove() protetto. Costruttore (id, props, v) per il mapper; static create(…) con v = 0, che può ritornare un Result. I metodi cambiano props, che è protected. La v la carica il mapper della repository.
Campi opzionalideleted_at porta il soft delete ed è una decisione di dominio, non un default. created_at e updated_at si mettono quando servono, con un motivo. Chi si cancella davvero espone un metodo di dominio (close(), reset()) che chiama remove().
Quando un'entityNon serve un'entity per ogni tabella. I registri append-only (log, storico dei passaggi) non sono entity: la loro riga si accoda nella stessa Unit of Work (append) e si scrive insieme alle entity.
Repository di un'entityLe letture che servono e un solo save(entity): void, che non scrive: accoda. Nuova → INSERT con v = 1; rimossa → controllo della versione e DELETE; altrimenti UPDATE con il controllo della versione. Niente upsert: un INSERT su un id che c'è già è un conflitto. Un'entity salvata due volte nella stessa esecuzione si scrive una volta, con l'ultimo stato.
Altre portePer ciò che non è un'entity la porta ha il metodo che serve (add per un registro, replaceAll per una tabella di configurazione), e accoda anch'esso nella Unit of Work. Una porta che scrive subito, fuori dalla Unit of Work, è un'eccezione da motivare.
Unit of WorkLa porta è minima: IUnitOfWork.runWithTransaction(work), che ritorna R | Err<never, ConflictError>. save, append e i controlli di versione sono dell'implementazione nell'adapter, che le repository ricevono come tipo concreto. Esegue work, poi scrive la coda in una transazione breve, tutto o niente. Le letture dentro work non vedono la coda: si legge, si decide, poi si scrive. La coda si scrive anche se work ritorna un errore (un save è la decisione di scrivere); si butta solo se work lancia.
GuardieUn save fuori da runWithTransaction lancia; due runWithTransaction sovrapposti sulla stessa uow lanciano. Uno use case eseguito due volte in sequenza riusa la uow, che si svuota a ogni giro.
ConflittoUna versione vecchia o un vincolo di unicità violato fanno fallire la transazione intera; li riconosce l'adapter, ogni altro guasto è un'eccezione. work si ripete da capo, tre volte in tutto, poi resta ConflictError (nel contract). Se una riga è stata cancellata nel frattempo, l'UPDATE non tocca niente e si vede solo a transazione confermata: il resto è scritto, e torna ConflictError senza ripetere.
Chi vinceDi default, fra persone vince l'ultima scrittura e la v non passa nei form. Quando una persona decide su ciò che ha visto (un passaggio di stato, un'approvazione), lo use case è «o va o errore»: la v arriva nell'input, lo use case la confronta con quella letta dentro work e risponde Outdated<X>Error. La ripetizione resta: rilegge e dà l'errore di dominio.
NomiPorta IUnitOfWork, simbolo UnitOfWork, variabile sempre uow. Mai «DatabaseContext».
ScopeUna Unit of Work per esecuzione di use case: inRequestScope di Inversify è una risoluzione, e ogni resolveUseCase(key) è una risoluzione nuova. Sono inRequestScope la Unit of Work, gli use case e le repository che ricevono la uow; il resto può essere costante.
-- colonna: v INTEGER NOT NULL DEFAULT 1 (su una tabella esistente: ALTER TABLE … ADD COLUMN)
UPDATE expense SET …, v = CASE WHEN v = ?letta THEN v + 1 END WHERE id = ?

Con una versione vecchia il CASE dà NULL, il vincolo fa fallire l'UPDATE e il database annulla tutto il batch. Contare le righe toccate basta solo dove la transazione è interattiva.

Vincoli
  • Il vincolo di unicità va sulla cosa che deve essere unica, non su un valore che la contiene: un progressivo ha la sua colonna e il suo UNIQUE
  • Con il soft delete il vincolo è parziale: UNIQUE … WHERE deleted_at IS NULL
  • Un codice scelto dall'utente come chiave fa coincidere unicità e conflitto: la ripetizione rilegge e dà l'errore di dominio giusto
Regole fra più righe
  • La versione protegge una riga, non una regola fra righe («resta almeno un amministratore»)
  • Una regola così si controlla dentro la transazione, nello stesso CASE: CASE WHEN v = ? AND (sottoquery) THEN v + 1 END; oppure con un'entity che la tenga

7DI e composition root

ChiCosa fa
composition root (apps/*, il seed, ogni test)Crea il container, new Container({ defaultScope: "Singleton" }); chiama install(container) del core; carica gli install degli adapter che ha scelto, passando la loro configurazione; lega i servizi che il core implementa da sé. Un container per composition root: due processi che si parlano in un test restano due container.
coreEspone install(container): void, che carica i moduli degli use case, e createUseCaseResolver(container): UseCaseResolver. Non crea il container e non ha singleton.
adapterEsporta install<Tecnologia>(opts): ContainerModule con i suoi binding (installD1({ DB }), installSqlServer({ host, … })). La configurazione entra da opts.
simboliPorte e servizi con InternalSymbols (Symbol.for); gli use case con la chiave stringa del registro.
// apps/webapp/workers/bootstrap.ts: env esiste solo nella richiesta, quindi si costruisce alla prima
let resolveUseCase: UseCaseResolver | undefined;

export function getResolveUseCase(env: Env): UseCaseResolver {
    if (!resolveUseCase) {
        const container = new Container({ defaultScope: "Singleton" });
        install(container);
        container.load(installD1({ DB: env.DB }));
        resolveUseCase = createUseCaseResolver(container);
    }
    return resolveUseCase;
}

Inversify e i suoi decoratori restano. Una migrazione futura a un altro container resta possibile finché il core usa solo l'iniezione nel costruttore e i binding stanno nei moduli e nelle composition root.

8L'input si valida al bordo

Chi chiama passa il dato dallo schema del contract (safeParse) solo dove entra un dato grezzo: il FormData di un'action, i parametri di una richiesta, il JSON di un canale. Un input che non lo rispetta è un 400 e lo use case non viene chiamato. Dove il valore è già tipizzato (l'utente della sessione, una costante, il seed) non si rivalida.

Al bordo di una webapp c'è uno schema del filo: trasforma le stringhe del form (campi ripetuti come elenco, numeri con la virgola, sì/no, spunte, JSON) e poi passa allo schema del contract con .pipe. Gli helper (leggiForm, leggiQuery, leggiParams) stanno nell'app, in un modulo .server.ts.

12Cosa diventa la skill

  • Una skill sola, blueprint, in inglese, con esempi su un dominio neutro (note spese). Le skill figlie e il plugin Core si tolgono.
  • Regole generali; i dettagli li decide la singola applicazione. Nessuna guida di migrazione.
  • Le ricette corte («come si aggiunge uno use case, un'entity, un errore, un modulo») sono il materiale che il progetto si copia nel suo CLAUDE.md e nei README.

Il quadro completo

Fin dove può arrivare un progetto costruito così. È il gradino più alto (2·C), non il punto di partenza: ogni pezzo compare solo quando c'è il segnale che lo giustifica (§1). Il disegno serve a vedere che i pezzi si aggiungono senza riscrivere quelli che c'erano.

Un contratto, molti client
  • Webapp, CLI e agenti chiamano gli stessi comandi con bus.dispatch
  • Il canale (RPC, HTTP, in-process) si cambia senza toccare chiamanti e handler
  • I client importano commands e core/client, mai use case e adapter
Un punto di controllo
  • Input validato una volta, dal dispatcher
  • Permessi applicati una volta, dal middleware, con la policy obbligatoria per ogni comando
  • Dati e segreti in un solo deployable
Un core che non cambia
  • Gli use case sono gli stessi dal gradino 1: cambia chi li chiama, non come sono scritti
  • Gli adapter si sostituiscono; lo stub fa girare tutto senza infrastruttura
  • Il lavoro differito passa dalla coda e chiama gli stessi use case

1Gradini

Un progetto parte dal gradino più basso che basta e sale quando compare il segnale. Ogni gradino aggiunge pacchetti; la mossa per salire è un refactor, a patto che le regole del §3 valgano dal primo giorno. Nei diagrammi le frecce indicano «importa».

// webapp: il loader chiama lo use case
export async function loader({ params, context }) {
    const result = await context
        .resolveUseCase("expenses.GetExpense")
        .execute({ expense_id: params.id },

    "approveExpense",

Segnale
Client che non possono ospitare il core (CLI, MCP, agenti, client non JS); dati e segreti in un solo deploy; dipendenze pesanti fuori dalle webapp quando i profili non bastano; regole d'accesso che andrebbero riscritte in ogni webapp.

Per ogni use case esposto: un comando con la sua policy in commands e un handler in bus. I client chiamano bus.dispatch.
Canale in-process

Pacchetti
+2, più il deployable del bus
Costo
Un salto di rete; un token che lo attraversa; un contratto da tenere compatibile fra deploy che non escono insieme.

2Strati e responsabilità

Al gradino 2·C. Ogni strato risponde a una domanda sola.

Criterio: se la risposta dipende da chi è l'attore rispetto alla risorsa (ruolo, appartenenza, possesso) è policy; se dipende dallo stato della risorsa è dominio. «Solo l'autore invia la nota» è policy, «solo se è in bozza» è dominio. Il resto lo decide l'applicazione.

3Use case

Fa
  • Assume che l'input sia del tipo dichiarato: la forma l'ha già controllata il bordo
  • Applica le regole di dominio attraverso entity e value object
  • Controlla i campi opzionali dove la logica lo richiede
  • Usa l'attore come dato (autore, chi approva), non per decidere i permessi
  • Apre una transazione solo se ci sono due o più scritture che devono riuscire o fallire insieme
  • Ritorna sempre un Result: successo o errore con nome, anche quando non può fallire
Non fa
  • Autenticazione o autorizzazione
  • Rivalidare a runtime ciò che il tipo garantisce
  • Leggere richiesta, cookie, variabili d'ambiente
  • Ricevere argomenti posizionali

Use case che chiamano use case

La regola «gli use case non chiamano altri use case» viene dalla skill attuale (conventions.md, regola 4 di SKILL.md), con due motivazioni: transazioni annidate e una catena di audit poco leggibile. La nota del 23/08 conta 23 casi in due progetti. Con l'autorizzazione fuori dagli use case e l'audit tolto dagli use case, la prima motivazione resta e la seconda no. Deciso: consentito, alle condizioni sotto.

L'unit of work di Prisma è già rientrante. Tiene però la transazione corrente in un campo dell'istanza: deve vivere per richiesta, non come singleton, altrimenti due richieste concorrenti nello stesso processo se la contendono. Il template in stack/ lo fa così e ha un test sulla concorrenza.

Test

  • dal gradino 2·A ogni use case ha test contro lo stub;
  • dal gradino 2·C il test di contratto del bus gira su entrambi i canali, con lo snapshot delle policy;
  • i fake in memoria rispettano i vincoli reali del database (indici unici, filtri) e lo dichiarano.

Fixture, factory e struttura delle cartelle dei test sono preferenze, in stack/.

4Risoluzione degli use case

5Command bus

Il chiamante invia un comando e attende l'esito; non sa su quale canale viaggia né dove gira l'handler. In-process, Workers RPC o HTTP: la chiamata è la stessa e restituisce una Promise dell'esito.

TermineCos'èDove sta
CommandIl messaggio: nome, schema dell'input, schema dell'output, kind, descrizione, policycommands
QueryUn comando con kind: "query": non modifica lo statocommands
BusL'oggetto con dispatch(nome, input); il tipo deriva dalla mappa dei comanditipo in commands, implementazione in bus
HandlerTraduce il comando nello use case: chiave del registro, toUseCase, fromUseCase?bus
MiddlewareStrati attorno a ogni handler: policy, audit, loggingbus
CanalePorta il comando dal chiamante al dispatcher e ne riporta l'esito: HTTP, RPC, in-processbus (adapter)
// commands/src/approveExpense.ts
export default command({
    input: z.object({ expense_id: z.string() }),
    output: expenseDto,
    kind: "mutation",
    description: "Approva una nota spese inviata",
    policy: can("expenses.approve"),
});
// bus/src/handlers/approveExpense.ts
export default handler(commands.approveExpense, {
    useCase: "expenses.ApproveExpense",
    toUseCase: (input) => input,
});

// handlers: { [K in keyof Commands]: Handler<Commands[K]> }
// un comando senza handler non compila

Dove si valida l'input

Lo schema sta nel comando, perché è contratto condiviso: il client può usarlo per validare prima di inviare, per dare un errore subito. Ma vale solo il controllo fatto dove il comando arriva: su un canale remoto può arrivare qualunque cosa. Il dispatcher del bus valida l'input contro lo schema prima della policy e dell'handler; se non passa, ritorna un errore di validazione e l'handler non viene chiamato. Così l'handler riceve sempre un input del tipo dichiarato, e lo use case dietro di lui può fidarsi. Sul canale in-process la validazione gira lo stesso.

Fino al gradino 2·B lo stesso ruolo lo ha la route, con lo stesso strumento di validazione.

Si chiama solo bus.dispatch(nome, input), mai una forma alternativa. Pacchetti: commands (contratto), bus (dispatcher, handler, middleware, canali), bus-server (deployable). Nomi delle funzioni indicativi: si fissano nel progetto esempio.

Cosa importano i client

Il peso non sta nel core ma negli adapter. Un core senza tecnologia e tree-shakeable ("sideEffects": false, un'uscita core/client separata da quella server) si importa a cuor leggero: DTO, tipi, dizionari, errori, funzioni pure. Le webapp lo fanno a ogni gradino, invece di duplicare codice. Quello che un client non importa mai sono use case, container e adapter.

Gli errori che attraversano il bus: il comando dichiara nello schema dell'output i suoi errori con nome, presi dal core. Il client li distingue in modo esaustivo; tutto ciò che non è dichiarato arriva come errore interno generico, senza dettagli.

6Middleware e policy

Chi sa le regole, chi le applica

Le regole d'accesso le conosce il core, come conosce l'attore: un servizio di autorizzazione risponde, dato lo use case, l'input e il contesto, se l'attore può procedere, se la risorsa non è sua o se non è autenticato. Anche identificare l'attore a partire da una credenziale (sessione, token) è un servizio del core. Come lo fa (stato sul database, token, attore ricaricato o no) lo decide l'applicazione.

Chi applica le regole cambia col gradino. Fino al 2·B è ogni webapp, che chiama il servizio per ottenere il contesto e deve farlo correttamente su ogni route: una route può avere più contesti possibili, e nessun meccanismo unico lo impone. Al 2·C le applica il middleware del bus, una volta per tutti i client: è uno dei motivi per salire.

Policy obbligatoria
  • Dato nel comando: CLI e agenti la leggono
  • Accessibile a ogni utente autenticato: anyMember, scritto esplicitamente
  • Nessun accesso anonimo: il bus si apre solo con un token valido
  • Scartati i default: «nega se manca» sposta l'errore a runtime, «consenti se manca» lascia buchi silenziosi
Verifica
  • Snapshot test versionato con comandi e policy: ogni cambio di permessi compare nel diff della PR
  • Test di contratto scritto una volta, eseguito sul canale in-process (stub) e su quello remoto
  • Middleware finto nei test: riceve nome del comando, attore, input ed esito senza conoscere l'handler

7Job, coda e cron

Il command bus astrae come si fa una chiamata (HTTP, RPC, in-process) e restituisce subito l'esito. Una job queue fa un'altra cosa: mette in coda un lavoro che un consumer esegue più tardi, con i suoi tempi, i suoi retry e il suo parallelismo. Sono due componenti distinti e si possono usare insieme.

Quello che il blueprint fissa è poco:

  • il lavoro differito passa da una porta del core; coda e scheduler sono adapter, con il loro stub;
  • il bus non sostituisce la coda, e la coda non sostituisce il bus;
  • chi esegue un job chiama lo use case, che resta quello di sempre e non sa di girare in differita.

Il resto (dove girano consumer e scheduler, retry, parallelismo, repliche, idempotenza, attore dei job) dipende dal progetto e dalla piattaforma. Il blueprint non lo prescrive: va deciso con calma, progetto per progetto, e diventerà una reference solo quando ci sarà una soluzione provata.

Effect: cosa si prende
  • Il modello: ogni operazione fallibile ritorna successo o errore con nome, errori taggati, schema per validare al bordo
  • Lo si rende obbligatorio negli use case (§3)
  • Si può adottare la libreria per i soli valori (Result, Data.TaggedError, Schema) oppure tenere la nostra con la stessa forma
Effect: cosa non si prende
  • Il runtime: use case come Effect<A, E, R>, porte come Context.Tag, adapter come Layer
  • Restano classi, iniezione nel costruttore, execute(input, ctx), il command bus del §5

Cambiare libreria di DI

Oggi ogni use case porta @injectable() e @inject(Symbol) di Inversify. tsyringe e TypeDI hanno decoratori con la stessa forma, quindi il passaggio è un codemod, se il core rispetta tre condizioni:

  • solo iniezione nel costruttore, con simboli o token propri del progetto;
  • nessuna funzione specifica del container nel core (binding con nome, scope esotici, container.get negli use case);
  • i binding stanno tutti nei moduli e nel composition root.

Ricerca fatta: Inversify 8, tsyringe e TypeDI richiedono ancora i decoratori legacy; TypeDI è abbandonato; esbuild non emette i metadata dei decoratori, e il core regge perché ogni parametro ha un @inject(Symbol) esplicito. L'alternativa senza decoratori (factory nei moduli, per esempio toResolvedValue) renderebbe il core indipendente dal container. Deciso: per ora restano Inversify e i suoi decoratori. Una migrazione futura costa di più, ma resta fattibile se valgono le tre condizioni sopra.

Deciso: i valori (risultato, errori con tag, schema) vengono da Effect 4; i nostri pacchetti result, maybe e tagged-error si ritirano. La PR #31 non si fonde. I progetti esistenti restano come sono: la skill non contiene una guida di migrazione.

12Vocabolario

Copia di CONTEXT.md alla radice di lib, in inglese come la skill. La fonte è lì.

TermineSignificatoDa evitare
RungOne of the shapes a project can take — 0, 1, 2·A, 2·B, 2·C — each adding packages to the one before.level, stage, tier
SignalThe concrete need that justifies climbing to the next rung.trigger, reason
MoveThe refactor that takes a project from one rung to the next without rewriting it.migration, upgrade
CoreThe package holding entities, value objects, use cases and ports, with no knowledge of any technology.domain package, backend
Use caseOne business operation: takes an input object and an execution context, returns a Result.service, interactor, action
Execution contextWhat a use case receives besides its input — at least the actor.request, session
ActorWho is performing the operation, as the core knows them.user, caller, principal
PortAn interface in the core for anything outside the process: storage, mail, queue, clock, token signer.gateway, provider
AdapterA package that implements one or more ports with a concrete technology.driver, plugin, infrastructure
StubThe in-memory adapter that implements every port, used for mock mode and for tests.fake, mock adapter
BootstrapThe package that loads the core and chooses its adapters, real or stub, for a deployable.container, composition package
ProfileA variant of the bootstrap that loads only the adapters one deployable needs.preset, flavour
PolicyThe rule that says whether an actor may perform a use case on a given input.permission, guard, ACL
CommandThe contract for one exposed use case: input and output schemas, kind, description, policy.operation, endpoint, RPC method
HandlerThe code that turns a command into a call to its use case.operation, resolver, controller
MiddlewareA layer wrapped around every handler, such as policy enforcement, audit or logging.decorator, interceptor
ChannelHow a command travels from the caller to the bus and its result comes back: in-process, HTTP, RPC.transport, protocol
Bus serverThe deployable that hosts the bus, its handlers and the bootstrap.API worker, API server
Job queueThe port through which work is scheduled to run later, outside the call that requested it.bus, outbox
ConsumerThe process that takes jobs from the queue and runs their use cases.worker

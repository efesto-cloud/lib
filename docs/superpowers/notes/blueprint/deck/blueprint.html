Il blueprint di Efesto

Come costruiamo un'applicazione perché resti elastica: le forme che prende crescendo e le parti di ciascuna.

30 ottobre 2026 · documento di lavoro, in revisione

Efesto

Dove può arrivare un progetto

L'immagine di tutto quello che ci sta davanti. In alto i client, il lato driver: due webapp via Workers RPC, una CLI sull'API HTTP, un server MCP per gli agenti. Tutti passano dallo stesso bus server: il canale porta il comando, il dispatcher valida l'input con lo schema del comando, il middleware applica la policy (un solo punto di autorizzazione, nessun accesso anonimo) e scrive l'audit, l'handler chiama lo use case. Il bus server carica il bootstrap, che compone il core con gli adapter driven: database, mail, coda dei job, e lo stub in memoria per mock e test. A parte la job queue: il consumer chiama gli stessi use case, più tardi.
Efesto

Come si legge il quadro

È il punto d'arrivo possibile, non il punto di partenza

  1. Si parte in bassoDal gradino più basso che basta al progetto.
  2. Compare il segnaleUn bisogno concreto che il gradino attuale non regge.
  3. Si fa la mossaUn refactor verso il gradino dopo. Niente riscrittura.

Si sale senza riscrivere solo se le regole dello use case valgono dal primo giorno.

Elasticità vuol dire questo: salire quando serve, non prima, e senza buttare via il codice. Ogni gradino aggiunge pacchetti a quello prima. La condizione è che le regole sugli use case (input oggetto, contesto, Result, niente autorizzazione dentro) si rispettino già al gradino 1.
Efesto

Gradini

Due assi, cinque gradini

Ogni gradino aggiunge pacchetti a quello prima. Le caselle fuori percorso sono possibili ma rare. Nei diagrammi dei gradini le frecce indicano «importa».
Efesto

Gradino 0

Un pacchetto: tutto sta nell'app

// app/routes/expenses.$id.tsx
export async function loader({ params }) {
    const expense =
        await db.expense.findUnique({
            where: { id: params.id },
        });
    if (!expense) throw notFound();
    return { expense };
}
  • Per: proof of concept, applicativi piccoli e autocontenuti.
  • Pacchetti: uno. Route, logica e query nello stesso posto.
  • Limite: la logica non si riusa e non si testa senza database.
Efesto

Gradino 1

La logica esce dall'app ed entra nel core

// webapp: il loader chiama lo use case
const result = await context
    .resolveUseCase("expenses.GetExpense")
    .execute({ expense_id: params.id },
             { actor: context.actor });
return toResponse(result);
  • Segnale: la logica serve a un secondo consumatore (un job, una CLI) o supera la prima schermata.
  • Mossa: la logica passa per intero in core; i loader chiamano use case.
  • Limite: le implementazioni delle porte stanno nel core e si portano dietro l'ORM.
È la forma della maggior parte delle applicazioni. Due pacchetti: core e webapp. Il limite: niente stub, niente test isolati.
Efesto

Gradino 2·A

Ogni porta ha un adapter reale e uno stub

// webapp/app/container.server.ts
container.load(
    env.MOCK
        ? installStub()
        : installDb({ db: env.DB }),
    installMail({ from: env.MAIL_FROM }),
);
  • Segnale: test senza infrastruttura, un mock navigabile prima del backend, un fornitore da poter cambiare.
  • Mossa: le implementazioni vanno in adapters/*, si aggiunge lo stub, l'app sceglie cosa caricare.
  • Limite: il wiring vive nell'app; un secondo processo dovrebbe ricopiarlo.
Il core non contiene più nessuna tecnologia. Pacchetti: due, più uno per adapter.
Efesto

Gradino 2·B

Più processi, un bootstrap con un profilo ciascuno

// webapp-admin/workers/app.ts
const resolveUseCase =
    await bootstrapAdmin(env, {
        mock: env.MOCK === "1",
        requires: ["DB", "MAIL_FROM"],
    });
  • Segnale: un'altra webapp, un consumer di code, un cron sullo stesso core.
  • Mossa: il composition root diventa il pacchetto bootstrap. Un binding mancante è un errore con nome.
  • Limite: ogni processo controlla i permessi per conto suo: le stesse regole, scritte più volte.
Il profilo carica solo gli adapter che servono a quel processo: le dipendenze pesanti (per esempio un adapter per le immagini) restano fuori dalle webapp che non le usano. Una porta senza binding fa fallire solo lo use case che la usa, con un errore esplicito.
Efesto

Gradino 2·C

Gli use case esposti diventano comandi

// webapp: chiama il bus, non il core
const result = await bus.dispatch(
    "approveExpense",
    { expense_id },
);
  • Segnale: client che non ospitano il core (CLI, MCP, agenti); regole d'accesso da riscrivere in ogni webapp.
  • Mossa: per ogni use case esposto, un comando con la policy e un handler.
  • Costo: un salto di rete, un token che lo attraversa, un contratto da tenere compatibile.
Altri segnali: dati e segreti in un solo deploy; dipendenze pesanti fuori dalle webapp quando i profili non bastano. Il gradino nasce col canale remoto (Workers RPC, HTTP). Il canale in-process non è un gradino a sé: serve alla mock mode e al test di contratto sullo stub. Pacchetti: commands, bus, più il deployable bus-server.

Efesto

Use case

Un oggetto e un contesto in ingresso, un Result in uscita

Fa

  • Si fida del tipo dichiarato
  • Applica le regole tramite entity e value object
  • Usa l'attore come dato, non per i permessi
  • Ritorna sempre un Result

Non fa

  • Autenticazione o autorizzazione
  • Rivalidare ciò che il tipo garantisce
  • Leggere richiesta, cookie, ambiente
  • Ricevere argomenti posizionali
Il vincolo sta in IUseCase: il tipo di ritorno deve essere un Result, altrimenti non compila. Così route, handler, job e altri use case trattano allo stesso modo successo e fallimento. Una transazione si apre solo se ci sono due o più scritture che devono riuscire o fallire insieme. Lo use case si chiama senza suffisso: ApproveExpense, interfaccia IApproveExpense, chiave DI "expenses.ApproveExpense".
Efesto

Use case

Uno use case può chiamarne un altro, a condizioni

  • Dipendenza per interfaccia, iniettata via DI.
  • Stesso contesto passato allo use case chiamato.
  • Una transazione sola: l'unit of work è rientrante e vive per richiesta, non come singleton.
  • Nessun ciclo fra use case.
La regola precedente vietava la composizione per due motivi: transazioni annidate e catena di audit poco leggibile. Con autorizzazione e audit fuori dagli use case resta solo il primo, che l'unit of work rientrante risolve. L'unit of work tiene la transazione corrente in un campo dell'istanza: se fosse singleton, due richieste concorrenti nello stesso processo se la contenderebbero. Il template in stack/ ha un test sulla concorrenza.
Efesto

Policy e dominio

Chi è l'attore è policy, com'è la risorsa è dominio

Policy

Dipende dall'attore rispetto alla risorsa: ruolo, appartenenza, possesso.

«Solo l'autore invia la nota»

Fuori dallo use case: la route fino al 2·B, il middleware del bus al 2·C.

Dominio

Dipende dallo stato della risorsa.

«Solo se è in bozza»

Dentro lo use case, attraverso l'entity.

I casi che il criterio non copre li decide l'applicazione.

Le regole d'accesso le conosce il core: un servizio di autorizzazione risponde, dato use case, input e contesto, se l'attore può procedere, se la risorsa non è sua o se non è autenticato. Anche identificare l'attore da una credenziale è un servizio del core. Cambia chi le applica: fino al 2·B ogni webapp, route per route, senza un meccanismo unico che lo imponga; al 2·C il middleware del bus, una volta per tutti i client.
Efesto

Command bus

Si chiama solo bus.dispatch, qualunque sia il canale

  1. ChiamanteInvia nome e input. Non sa dove gira l'handler.
  2. CanaleIn-process, Workers RPC, HTTP. Sostituibile.
  3. DispatcherValida l'input con lo schema del comando.
  4. MiddlewarePolicy, audit, logging.
  5. HandlerTraduce il comando nello use case.

Il ritorno è sempre una Promise dell'esito. Il bus non ha code e non differisce niente.

Il chiamante non sa su quale canale viaggia il comando né dove gira l'handler. Il canale in-process serve alla mock mode e ai test di contratto. Pacchetti: commands (contratto), bus (dispatcher, handler, middleware, canali), bus-server (deployable). Un comando senza handler non compila. I nomi delle funzioni sono indicativi: si fissano nel progetto esempio.
Efesto

Command bus

Il comando è il contratto fra client e bus

// commands/src/approveExpense.ts
export default command({
    input: z.object({
        expense_id: z.string(),
    }),
    output: expenseDto,
    kind: "mutation",
    description: "Approva una nota spese",
    policy: can("expenses.approve"),
});
  • Schema: il client può validare prima di inviare; fa fede il controllo del dispatcher.
  • Errori: con nome, dichiarati nell'output. Il resto arriva come errore interno generico.
  • Client: importano commands e core/client; mai use case, container, adapter.
Su un canale remoto può arrivare qualunque cosa: il dispatcher valida prima della policy e dell'handler, anche in-process. Se l'input non passa, torna un errore di validazione e l'handler non viene chiamato. Il core è tree-shakeable, con un'uscita core/client separata da quella server: DTO, tipi, dizionari, errori, funzioni pure. Il peso sta negli adapter, non nel core.
Efesto

Middleware e policy

Nessun comando senza policy

La regola

  • La policy è un dato: CLI e agenti la leggono
  • Aperta a ogni autenticato: anyMember, esplicito
  • Nessun accesso anonimo: serve un token valido
  • Nessun default: né «nega» né «consenti» se manca

La verifica

  • Snapshot versionato di comandi e policy: ogni cambio di permessi è nel diff della PR
  • Test di contratto sui due canali, in-process e remoto

Da decidere: dove si dichiara la policy di uno use case. Gli esempi la mettono nel comando.

Nei test un middleware finto riceve nome del comando, attore, input ed esito senza conoscere l'handler. I default sono stati scartati: «nega se manca» sposta l'errore a runtime, «consenti se manca» lascia buchi silenziosi. Il middleware è una funzione che avvolge l'handler, applicata una volta da chi costruisce il bus; l'handler non sa chi lo avvolge.
Efesto

Job, coda e cron

Il bus risponde subito, la coda esegue dopo

Il blueprint fissa

  • Il lavoro differito passa da una porta del core
  • Coda e scheduler sono adapter, con il loro stub
  • Il consumer chiama lo use case di sempre

Resta al progetto

  • Dove girano consumer e scheduler
  • Retry, parallelismo, repliche, idempotenza
  • L'attore dei job
Il bus non sostituisce la coda e la coda non sostituisce il bus; si possono usare insieme. Lo use case non sa di girare in differita. Il resto diventerà una reference solo quando ci sarà una soluzione provata.

Librerie in lib

Meno pacchetti: i valori da Effect 4, il resto si tiene

Si tiene

entity, usecase (col vincolo sul Result), unit-of-work, expand, metadata, teardown, publisher, observable, react-observable, computed

Si ritira

result, maybe, tagged-error e affini → Effect 4. I pacchetti per ORM → template in stack/. login-session, audit.

Da rivedere

toast, da riallineare. env, da far girare dove process non c'è. outbox, sospeso con i job.

Da Effect solo i valori, non il runtime. Inversify e i decoratori restano, per ora.

Effect: si prende il modello (successo o errore con nome, errori taggati, schema al bordo); non si prende il runtime (Effect come use case, Context.Tag, Layer). Restano classi, iniezione nel costruttore, execute(input, ctx). Inversify: un passaggio futuro a tsyringe o TypeDI resta un codemod se il core usa solo iniezione nel costruttore con simboli propri, nessuna funzione specifica del container, binding tutti nei moduli e nel composition root. I progetti esistenti restano come sono: niente guida di migrazione.

Gli snippet della skill si prendono da qui: compilano e hanno i test.

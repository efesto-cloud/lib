## Cosa

Ogni use case ha **una policy**, e **il resolver** la controlla prima di eseguirlo. Questo passo costruisce il meccanismo e dà la policy a tutti i 50 use case di oggi. Agli use case delle pratiche ne dà una provvisoria, `AnyUtente`, che #105 sostituisce con le azioni della matrice.

### Contract

- **`NotAllowedError`** nella forma di better-result, come `errors/ConflictError.ts`: `class NotAllowedError extends TaggedError("NotAllowedError")<{ regola: string }> {}`. `regola` dice cosa non è passato: il nome della policy, o la chiave dell'azione.
- **Il tipo del resolver** aggiunge `NotAllowedError` agli errori di ogni use case, una volta per tutti.

### Core

- **La forma della policy**: una classe `@injectable()` con `check(target, ctx): Promise<Result<void, NotAllowedError>>`. Il suo `static on(select)` la rende già pronta, con la mappatura dall'input dentro (`.on((i) => i.codice)`, `.on((i) => i.codice_commessa)`, `.on((i) => i.bu)`). Le policy che non guardano l'input si scrivono nude.
- **Le policy di questo passo**:
  - `Anyone`: chiunque, anche senza utente;
  - `AnyUtente`: c'è un utente nel contesto. Non guarda `cambio_password`, che resta compito del guscio;
  - `OnlyAmministratore`.
- **`packages/core/src/auth/policies.ts`**, una riga per use case. Il tipo richiede ogni chiave del registro, quindi uno use case senza policy non compila.
  - **`accesso`**:
    - `Login` e `SeedUtenti` → `Anyone`, perché partono prima del login;
    - lo use case del rinnovo di #103 → `Anyone`, perché lo chiama il bordo con l'id preso da un token già verificato;
    - `ChangePassword` → `AnyUtente`.
  - **`utenti`**: `ListUtenti` → `AnyUtente`, perché la usano le pagine delle pratiche per scegliere la squadra. `CreateUtente`, `UpdateUtente`, `ResetPassword` e `DeleteUtente` → `OnlyAmministratore`.
  - **`clienti`**: `ListClienti`, `ListRagioniSociali` e `CreateCliente` → `AnyUtente` (il cliente si crea al volo dalla nuova offerta). `RenameCliente` e `AssignRagioneSociale` → `OnlyAmministratore`.
  - **`arca`**: `SendHeartbeat`, `SyncArcaToCloud`, `RecordHeartbeat`, `StoreSyncBlock` e `RecordSyncFailure` → `Anyone`. L'autenticazione la fa il bordo, cioè la firma HMAC sulle route (#50). Se una route della webapp ne chiamasse uno senza utente, la colpa sarebbe sua (ADR 0012). Va scritto nel commento della riga. `GetProbeStatus` → `OnlyAmministratore`, perché lo legge solo Impostazioni.
  - **`offerte` e `commesse`**: `AnyUtente`, provvisoria, con un commento che rimanda a #105.
- **Il resolver** resta **uno per Worker** (`workers/bootstrap.ts`). Avvolge `execute` e controlla la policy sul `ctx` **di quella chiamata**:
  ```ts
  return (key) => ({
      async execute(input, ctx) {
          // policy e use case nello stesso request scope: vedi sotto
          const { useCase, policy } = resolveTogether(container, key);
          const allowed = await policy.check(input, ctx);
          if (allowed.isErr()) return allowed;
          return useCase.execute(input, ctx);
      },
  });
  ```
  **Il vincolo**: policy e use case si risolvono **nello stesso request scope**. Gli use case sono `inRequestScope` (`di/useCaseModule.ts:19`), e due `container.get` separati darebbero alla policy una Unit of Work diversa da quella dello use case. Come ottenerlo lo sceglie chi implementa, per esempio un oggetto che si fa iniettare entrambi, o un child container per chiamata. Un test lo dimostra.
- **Niente `onActivation` di Inversify.** Gli use case che un altro use case si fa iniettare non passano dalla policy (oggi non ce ne sono).

## Fatto quando

- Uno use case senza riga in `policies.ts` non compila (test di tipo).
- Un utente non Amministratore che chiama `utenti.UpdateUtente` o `arca.GetProbeStatus` riceve `NotAllowedError`, e lo use case non viene eseguito.
- Una chiamata senza utente a uno use case `AnyUtente` riceve `NotAllowedError`.
- Policy e use case vedono la stessa Unit of Work (test).
- Uno snapshot versionato della mappa use case → policy compare nel diff di ogni PR che cambia un permesso.
- Login, cambio password, gestione utenti, pratiche e sonda funzionano come prima. I test sono verdi in tutti i pacchetti.
- Ci sono l'ADR e `docs/permessi/`.

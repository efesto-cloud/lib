# #89 Entity con versione, un solo save e scritture in coda (Unit of Work)

Part of #41

Deciso con Dario l'11/11/2026, rileggendo #72 e #78. Passo dell'epic dopo #88 e prima di #73.

**Blocked by**: #88 (la forma del contract).

## Perché

Il Blueprint prevede entity con una versione e repository con un solo `save`; il CRM ha una sola entity scritta a mano (`Utente`, senza versione), record sparsi trattati come valori (`Sessione` è un'interfaccia dentro la porta, `TentativiAccesso` un valore passato al repo) e repository con metodi diversi l'una dall'altra (`create` + `save`, `save` + `delete` + `deleteForUtente`). Le pratiche (#81) avranno più persone sullo stesso dato: il patto va fissato prima.

## Il patto

- **Entity con versione `v`**: 0 se nuova, poi cresce di uno a ogni salvataggio. La carica il mapper della repository, in modo trasparente: lo use case non la vede.
- **Un solo `save(entity)`** per repository di entity. Dentro sceglie: `isNew()` → INSERT (un `id` già esistente è un errore, non una sovrascrittura); altrimenti `UPDATE … SET …, v = v + 1` controllato sulla versione letta. Niente upsert. Più le letture che servono (`get`, `search`, query puntuali).
- **Scritture in coda, eseguite alla fine (Unit of Work)**: `save` non scrive, accoda. Una **Unit of Work** per esecuzione di use case, porta del core `IUnitOfWork` (simbolo `UnitOfWork`, abbreviato sempre `uow`, minuscolo; **mai** «DatabaseContext» né «contesto»: è il nome deciso nel Blueprint), con `runWithTransaction(callback)`: alla fine della callback esegue la coda in una transazione breve, tutto o niente. Su D1 è un `db.batch()`. Vale per tutti i database (Postgres, SQLite, D1, Mongo): nessuna riga resta bloccata mentre lo use case ragiona. **Le letture dentro la callback non vedono le scritture in coda**: lo use case legge, decide, poi scrive.
- **Il conflitto fa fallire la coda intera.** Contare le righe toccate basta dove la transazione è interattiva (Postgres, SQLite: 0 righe → ROLLBACK), ma non su D1: `db.batch()` restituisce i conteggi solo a batch già confermato, quando le altre scritture sono salvate e non si annullano più. Serve che l'istruzione fallisca da sola. Senza trigger, con la `v` `NOT NULL` (provato su `node:sqlite`):
  ```sql
  UPDATE Utente SET …, v = CASE WHEN v = ?letta THEN v + 1 END WHERE id = ?
  ```
  Con la versione vecchia il `CASE` dà `NULL`, il vincolo `NOT NULL` fa fallire l'UPDATE e il batch si annulla tutto. Funziona uguale su Postgres. Il caso di una riga che nel frattempo non c'è più (0 righe toccate) si legge dai conteggi del batch.
- **Sul conflitto `runWithTransaction` ripete la callback da capo** (rilegge, gli `if` dello use case ricontrollano, riaccoda), un numero fisso di volte; poi restituisce `Result<T, ConflictError>`, con `ConflictError` nel contract. Tra persone vince l'ultima scrittura: è la prassi dei gestionali, e niente `v` viaggia nei form.
  - **Da tenere presente, non da fare ora**: uno use case dove una persona decide su ciò che ha visto (un'approvazione sopra soglia, #83) vorrà «o va o errore»: la `v` arriva dall'input e la ripetizione si spegne. Il meccanismo lo permette senza cambiare il patto.
- **`deleted_at` solo dove il dominio lo vuole.** Il soft delete è una decisione di dominio, non un default; lo stesso vale per `created_at`/`updated_at`, che si mettono quando servono, con un motivo.

## Cosa

1. La base dell'entity **scritta nel core**, piccola (con `v`, `isNew()`; il soft delete solo per chi lo vuole), non `@efesto-cloud/entity`: quella è a 0.0.4, vuole luxon e mette `deleted_at` a tutte le entity (deciso con Dario: si corregge la libreria in un secondo tempo, dal registro per il Blueprint). La porta `IUnitOfWork` con `runWithTransaction` e `ConflictError`, l'implementazione D1 in `adapters/d1-adapter`.
2. **Diventano entity**: `Utente` (con `deleted_at`, come oggi), `Sessione`, `TentativiAccesso`, lo stato della sonda. Sessione e tentativi si cancellano davvero: niente `deleted_at`.
3. **Restano record con metodi puntuali**: ciò che è append-only, stile log (log dei giri, cambi di stato della sonda), i blocchi dell'ingresso e lo specchio di Arca. Un'entity base comune alle tabelle dello specchio si valuta con #62.
4. Le repository di quelle quattro entity passano al `save` unico; gli use case che scrivono passano da `runWithTransaction`.
5. Colonna `v INTEGER NOT NULL` nelle tabelle delle entity, in una migrazione.

6. **Ogni adapter esporta il suo install** (deciso con Dario l'11/11/2026, sul modello di `efesto-cloud/agent`): `installD1({ DB })`, `installSqlServer({ …, readSecret })`, `installHttp({ baseUrl, readSecret })`, `installStub()`, ognuno restituisce un `ContainerModule` con i suoi binding. Le composition root (`apps/webapp/workers/bootstrap.ts`, `apps/sonda/src/index.ts`, `apps/webapp/seed/index.ts`) si riducono a `new Container()`, l'install del core e gli install degli adapter. Per D1 è necessario: la Unit of Work è per esecuzione di use case (`inRequestScope`) e le repository la ricevono, quindi le costruisce Inversify (`@injectable()`, simboli), non più `toConstantValue(new …)`. Via l'`@injectable()` inutile di `StubArcaErp` se lo stub resta un valore costante.

## Fatto quando

- Due salvataggi della stessa entity a partire dalla stessa versione: il secondo fallisce, e annulla anche le altre scritture della sua coda (test su D1, miniflare).
- Un conflitto seguito da un tentativo riuscito dà il risultato dello stato nuovo (test).
- Nessuna composition root lega a mano i binding di un adapter: carica il suo install.
- Un test comune a tutte le repository di entity verifica il patto (nuova → insert; id esistente con `v = 0` → errore; versione vecchia → conflitto), così una repository nuova lo eredita.
